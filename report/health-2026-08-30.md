## 중대 고장 — 유지보수 단위 테스트 게이트가 CI에서 항상 실패한다

**무엇이 일어났나.** `weekly-collect.yml`의 `housekeeping` 잡이 오늘 01:20 KST에
정상 발화했다(run [33262686788](https://github.com/econ-blog/econ-blog.github.io/actions/runs/33262686788)).
`linkstate`와 `GA4/GSC` 잡은 성공했고 링크 원장 아티팩트도 올라갔다. 그런데
`Run Unit Tests` 스텝이 실패해 `Run Housekeeping`과 `Commit and Push`가
**둘 다 skipped** 됐다.

```
FileNotFoundError: [Errno 2] No such file or directory:
  '/home/runner/work/econ-blog.github.io/econ-blog.github.io/.venv/bin/python'
  at .claude/audit/lib/test_contracts.py, line 133 → run_cli("--check", "terms")
```

**원인.** 테스트가 서브프로세스로 CLI를 부를 때 인터프리터를 `.venv/bin/python`으로
**하드코딩**한다.

- `.claude/audit/lib/test_contracts.py:125` — `PY = str(REPO_ROOT / ".venv/bin/python")`
- `.claude/audit/lib/test_hypothesis.py:190` — `os.path.join(..., ".venv", "bin", "python")`

CI의 `housekeeping` 잡은 `actions/setup-python` + `pip install -r requirements.txt`로
붙고 `.venv`를 만들지 않는다. 테스트 러너도 `python "$f"`(맨 인터프리터)다. 그러므로
`.venv/bin/python`은 그 잡에 **존재한 적이 없다.**

**왜 지금까지 안 보였나.** 로컬과 점검 샌드박스는 `bootstrap.sh`가 `.venv`를 만들어
두므로 같은 테스트가 전건 통과한다. 이 결함은 `.venv`가 없는 환경에서만 뜨고,
그 환경은 CI의 이 잡 하나뿐이다. 그리고 이 잡은 2026-08-28 통합 이후 오늘이
**첫 발화**였다.

**뒤에 두 번째 지뢰가 있다.** 러너가 `|| exit 1`이라 `test_contracts.py`에서 멈췄고
`test_hypothesis.py`는 아직 돌지도 못했다. 앞엣것만 고치면 다음 주에 같은 예외가
뒷것에서 뜬다. 둘을 함께 고쳐야 한다.

**고칠 방법 — 검증까지 마쳤고, 적용만 남았다.**
두 파일의 `PY`를 `sys.executable`로 바꾼다. `scripts/test_read_snapshot.py:204`가
이미 그렇게 하고 있고 그 파일은 CI에서 문제를 낸 적이 없다 — 정답이 저장소 안에 있다.

```python
PY = sys.executable   # .venv 유무와 무관하게 지금 도는 인터프리터를 쓴다
```

말로만 제안하지 않았다. 저장소를 `.venv` 없이 복제해 CI와 같은 조건을 만들고 확인했다.

| | 결과 |
|---|---|
| 수정 전 | `test_contracts.py`에서 동일한 `FileNotFoundError`, 종료코드 1 — **CI 실패를 그대로 재현** |
| 수정 후 | `test_contracts.py` 34건 · `test_hypothesis.py` 77건 통과 |
| 수정 후 · CI 러너 전체(`test_*.py` 22개) | **전건 통과 — 세 번째 지뢰는 없다** |

즉 이 두 줄이 유지보수 축을 되살리는 데 필요한 전부다.
**무엇이 멈춰 있나.** 유지보수의 세 축이 전부 정지다 — ① 링크 · ④ 스캔 · ⑥ 수치.
파생 피해가 하나 더 있다: 회차 1이 `link-state.json`의 원장 단절을 고치려고 통합을
했는데, 원장을 커밋하는 주체가 바로 이 잡이다. `last_checked`는 2026-08-23에 묶인
채이고, `confirmed_dead`가 "하드 2회 + 5일"을 요구하므로 **어떤 죽은 링크도 사망
판정에 도달할 수 없다.** 리포트의 "확정 사망 0건"은 여전히 건강 신호가 아니라
계측이 멈춘 신호다.

**게이트 자체는 제대로 작동했다.** 승인 루프가 사라진 뒤 이 스텝이 유일한 안전장치이고,
그것이 의도대로 커밋을 막았다. 고장난 것은 게이트가 아니라 게이트가 딛고 선 발판이다.
