## 0. 모드 계약 (먼저 확인)

**이 명령은 로컬 대화형 전용이다.** 클라우드 세션에서 실행하지 않는다 — 이 명령이
하는 일은 전부 클라우드 샌드박스가 도달하지 못하는 것들이라, 거기서 돌리면 매 단계가
"확인 불가"로 끝나고 그 결과를 확인된 것처럼 적을 위험만 남는다.

맨 먼저 자신이 로컬인지 확인한다:

```bash
curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 https://www.hankyung.com/
```

`000`이 나오면 **클라우드다. 그 자리에서 중단하고** 사람에게 "로컬 세션에서 실행해
주세요"라고 알린다. 200번대가 나오면 계속한다.

무인 루틴에서 호출하지 않는다. `/daily-post`·`/audit-improvement`와 달리 이 명령은
사람이 브라우저에 로그인해 있는 것을 전제한다.

## 1. 대기열 읽기

`report/` 에서 **가장 최근** `audit-YYYY-MM-DD[-HHMM].md`를 찾아 `## 로컬 세션 대기열`
섹션을 Read한다. 파일명 정렬이 곧 날짜 정렬이다(`audit-` 접두사 + ISO 날짜).

- 섹션이 없거나 항목이 0건이면 **할 일이 없다.** 그대로 보고하고 끝낸다.
- 이미 `- [x]`로 체크된 항목은 건너뛴다. 지난 세션이 처리한 것이다.
- 항목 형식은 `- [ ] <축> · <대상> · <확인할 것> · <확인 뒤 할 일>`이다
  (`.claude/commands/audit-improvement.md` §8이 정한 형식 — 한쪽만 바꾸지 않는다).

`## 로컬 세션 대기열`이 통째로 없는 리포트는 §9-2 분류가 도입되기 전(2026-08-16 이전)에
만들어진 것이다. 그 경우 리포트의 `### 소견` 표들을 읽고 §2~§5의 축별 절차에 해당하는
것만 골라 사람에게 목록으로 제시한 뒤 확인을 받고 진행한다.

## 2. ③ 색인 제출 (GSC · 네이버)

리포트 ③의 `색인 요청 대상` 표가 입력이다. 서브에이전트를 쓴다:

- 구글: `google-submit` 에이전트
- 네이버: `naver-submit` 에이전트

두 에이전트 모두 **사용자가 이미 로그인한 실제 Chrome**을 쓰고 **제출은 매 건 사용자
승인을 받는다.** 그 규약을 이 명령이 완화하지 않는다 — 한 번에 전부 제출하라고
지시하지 않는다.

- 목록이 20건을 넘으면 **한 번에 전부 넣지 않는다.** 색인 요청에는 일일 할당량이 있고,
  넘기면 나머지가 조용히 실패한다. 포스트를 사전보다 먼저, 최신 글을 먼저 넣는다.
- 제출 결과(성공·할당량 초과·이미 색인됨)를 URL별로 받아 적는다. §6에서 쓴다.
- **색인은 제출한다고 되는 것이 아니다.** "제출됨"까지만 적고 "색인됨"이라고 쓰지 않는다.

## 3. ⑥ N1 — 원문에서만 확인되는 기준일

대기열의 `⑥ N1` 항목이 입력이다. 각 항목에 대해:

1. 해당 포스트의 front matter `source_url`을 읽는다.
2. WebFetch로 원문을 연다. **로컬에서는 동작한다** — 이것이 이 명령이 로컬 전용인 이유다.
3. 그 수치의 기준일이 원문에 **명시돼 있는 경우에만** 문장에 병기한다.

**원문에 없으면 지어내지 않는다.** 그 항목은 체크하지 말고 `- [ ]`로 남긴 채 사유를
한 줄 덧붙인다(`원문에 기준일 없음 — 수치 삭제 여부는 사람 판단`). 기사가 이미
내려갔거나(404) 유료화됐으면 같게 처리한다.

고친 뒤 파일별로 다시 돌려 0이 됐는지 본다:

```bash
.venv/bin/python .claude/audit/lib/numerics.py --file <파일경로>
```

`writing-styles.md`의 "지어내지 않기"가 그대로 적용된다. 검사를 통과시키려고 날짜를
채우는 것은 그 규칙 위반이며, N1 위반 하나보다 나쁘다.

## 4. ⑤ D4 — 1차 출처 소급 링크

대기열의 `⑤ D4` 항목이 입력이다. 붙일 수 있는 1차 출처는 다섯이다 —
ECOS(`ecos.bok.or.kr`) · FRED(`fred.stlouisfed.org`) · KOSIS(`kosis.kr`) ·
DART(`dart.fss.or.kr`) · 전국은행연합회 소비자포털(`portal.kfb.or.kr`).

- **URL을 열어 200이 나오는 것만 쓴다.** 딥링크(통계표 ID·조회 파라미터)를 추측하지
  않는다. 확신이 서지 않으면 기관 대문 주소를 쓴다.
- 그 글이 인용한 지표의 공시 기관이 다섯 목록 밖이면 **링크하지 않고 넘어간다.**
  비1차 출처를 대신 넣지 않는다. 목록 자체를 늘리는 것은 `사람 판정`이다
  (`audit-improvement.md` §9-2).
- 지정학·정책 발표·기업 개별 이슈처럼 공시 지표가 애초에 없는 글은 **대상이 아니다.**
  대기열에 올라와 있어도 그 사유를 적고 체크하지 않는다.

포스트 본문 산문은 건드리지 않는다. 링크만 건다.

## 5. ① 러너 도달 불가 의심 링크

리포트 ①의 `러너 도달 불가 의심` 표가 입력이다. 각 URL을 로컬에서 직접 연다:

```bash
curl -sS -o /dev/null -w "%{http_code} %{url_effective}\n" -L --max-time 20 "<URL>"
```

- 200번대면 **살아 있는 링크다.** GitHub Actions 러너 IP에서만 막힌 것이므로
  `content/`를 고치지 않는다. 사람에게 "러너 환경 문제"로 보고한다.
- 4xx/5xx가 로컬에서도 재현되면 확정 사망이다. 해당 `related_articles` 항목을 제거하거나
  링크를 걷어낸다 — `/audit-improvement`의 사망 링크 처리와 같은 규칙이다.
- **원장(`.claude/audit/link-state.json`)을 손으로 고치지 않는다.** 그 파일은
  `linkcheck.py`가 관리하며, 사람이 값을 넣으면 다음 주 2-strike 판정이 어긋난다.

## 6. 대기열 갱신과 게시

처리한 항목의 체크박스를 `- [x]`로 바꾸고, 처리하지 못한 항목에는 사유를 한 줄
덧붙인다. **항목을 지우지 않는다** — 지우면 다음 주 감사가 같은 것을 다시 올린다.

git은 여기서만 한다. 변경은 성격이 둘로 갈린다:

1. **리포트 대기열 체크 갱신**은 관측 기록이므로 `main` 직행이다.
2. **`content/` 수정**(N1 기준일 병기 · D4 링크 · 사망 링크 제거)은 승인 게이트를
   거친다. 파일 경로와 각 변경의 근거(원문 URL·확인한 날짜·상태코드)를 표로 제시하고
   "이 변경을 main에 푸시할까요?"로 묻는다. **명확한 긍정만 승인으로 인정한다** —
   "좋아요"·"괜찮네요"는 승인이 아니다.

승인 뒤:

```bash
git add <명시 경로>          # 글롭 금지
git commit -m "audit-local: <날짜> 대기열 처리"
git push origin main
```

**`auto/**` 브랜치에 아무것도 밀지 않는다.** 그 푸시는 `open-auto-pr.yml`을 깨우고,
이 시점에 PR을 만들 이유가 없다(`AGENTS.md` `/revise-post` 절과 같은 이유).

색인 제출은 커밋할 것이 없다 — §2의 결과는 대기열 체크와 사람에게 하는 보고로만 남는다.

## 7. 보고

끝에 네 줄로 보고한다. 없는 축은 줄을 생략한다.

```
③ 색인 제출: 성공 N건 / 할당량 초과 N건 / 이미 색인 N건
⑥ N1: 병기 N건 / 원문에 기준일 없어 보류 N건
⑤ D4: 링크 N건 / 대상 아님 N건
① 도달성: 살아 있음 N건 / 확정 사망 N건
```

숫자는 실제로 한 것만 센다. 시도했으나 실패한 것을 성공에 넣지 않는다.
