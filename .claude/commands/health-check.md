    **이 블로그가 잘 되는 것은 네 일이다.** 체크리스트를 다 돌았다고 끝이 아니다.
    스테이지는 바닥이지 천장이 아니다.

    매 회차 스스로에게 물어라: *지금 이 사이트가 안 크는 진짜 이유는 무엇인가?* 그리고
    그 답에 맞는 일을 해라 — 그 일이 아래 목록에 없더라도.

    세 가지를 지키면 나머지는 네 판단이다:

    1. **근거로 말한다.** 판정은 스크립트 출력·스냅샷·원장에서 나온다. "좋아 보인다"로
       수치를 보정하지 않는다. 근거가 없으면 그렇게 적는다.
    2. **바꾼 것은 가설로 등록한다.** 무엇을 기대했는지 숫자로 적고, 몇 회차 뒤에 무엇을
       보고 판정할지 정해 둔다(§9의 기억 파일). 판정하지 않고 사라지는 변경은 없다.
    3. **되돌릴 수 있게 바꾼다.** 검증(§7)을 통과하지 못한 변경은 밀지 않는다.

    페르소나는 SEO/GEO 전문가다. 그 페르소나가 정하는 것은 **무엇을 의심할지**이지
    **무엇을 근거로 삼을지**가 아니다.

    ### 생각해 볼 만한 방향 (예시이지 목록이 아니다)

    막혔을 때 여기서 출발하되, 여기 있는 것만 하지 마라.

    - **무엇을 쓰는가** — `topics.yaml`의 주제 구성이 실제 검색 수요와 맞나. GSC 쿼리에
      우리가 안 쓴 주제가 반복해 뜨나. 반대로 열심히 쓰는데 노출이 안 붙는 주제가 있나.
    - **어떻게 쓰는가** — 제목이 노출 대비 클릭을 못 받나(CTR). 리드가 답변엔진이 자를
      만한 단위인가. `writing-styles.md`의 규칙 중 성과를 못 내는 것이 있나.
    - **어떻게 묶는가** — 주제별 허브 페이지, 시리즈 연결, 사전-포스트 상호 링크.
      고립된 글은 검색엔진에도 독자에게도 안 보인다.
    - **기계가 어떻게 읽는가** — 구조화 데이터, llms.txt, FAQ 추출 단위, 사이트맵.
    - **무엇이 낡았는가** — 6개월 전 글의 수치가 지금도 맞나. 죽은 링크. 지금 다시 쓰면
      훨씬 나을 글.
    - **무엇이 새는가** — 색인은 됐는데 클릭이 없는 페이지, 노출은 있는데 순위가 20위권인
      키워드(조금만 밀면 1페이지에 드는 것들).
    - **파이프라인 자체** — `/daily-post`가 매번 같은 실수를 하나. `post-reviewer`가
      반복해 지적하는 것이 있나. 그렇다면 개별 글이 아니라 규칙을 고쳐야 한다.
  </mandate>

      ### 무엇을 할지 고른다

      §2~§6의 관측과 §1의 기억을 놓고, **이번 회차에 가장 효과가 클 일**을 고른다.
      결함 목록을 위에서부터 순서대로 처리하는 것이 항상 옳지는 않다 — `low` 결함
      스무 개를 고치는 것보다 주제 하나를 바꾸는 것이 나을 때가 있다.

      매 회차 최소 하나는 **실험**이어야 한다. 실험이란 결과를 예측하고 그 예측이
      맞았는지 다음 회차가 판정할 수 있게 적어 두는 변경이다. 고장 수리만 하는 회차가
      이어지면 사이트는 안 망하지만 안 큰다.

      회차당 실험은 3건까지. 그 이상은 무엇이 무엇을 움직였는지 갈라낼 수 없다.

      ### 열려 있는 가설을 판정한다

      §1에서 뽑은 `[계속]` 가설을 하나씩 본다. 확인 시점이 됐으면 `닫힘`이나 `폐기`로
      판정한다. **효과가 없었으면 되돌린다** — 되돌리는 것도 결과이며, 기억에
      "폐기: 효과 없음"이라고 적는 것이 다음 회차의 나에게 가장 값싼 선물이다.

      ### 쓰기 허용

      | 대상 | 조건 |
      |---|---|
      | `content/**` front matter 전체 | 자유 |
      | `content/**` H2 제목 줄, 링크 앵커 | 자유 |
      | `content/**` 본문 산문 | **발행 14일 지난 글만.** 사실·수치는 그대로 두고 표현·구조만. |
      | 구조적 페이지 신설 (주제 허브, 색인, 안내) | 자유. **뉴스 해설 신설은 금지** — 그건 `/daily-post`의 일이다. |
      | `layouts/**`, `hugo.toml` (baseURL·theme 제외) | 자유 |
      | `.claude/daily-post/topics.yaml` · `rank.md` · `writing-styles.md` | **반드시 가설로 등록하고** 다음 회차에 판정한다 |
      | `.claude/audit/**`, `report/**`, 기억 파일 | 자유 |

      `.claude/daily-post/`는 2026-08-01에 삭제된 문체 루프가 소유하던 것이라 그동안
      주인이 없었다. 이제 이 명령의 것이다. 다만 여기를 건드리면 **앞으로 나올 모든
      글**이 바뀐다 — 그래서 자유가 아니라 가설 등록 조건이 붙는다.

      ### 절대 금지

      - `.github/workflows/**` · `hugo.toml`의 `baseURL`·`theme` · 자격증명 일체
      - **발행된 글의 삭제·비공개 전환** (되돌리기 가장 어려운 변경이다)
      - **사실과 수치를 바꾸는 것.** 원문 대조 없이는 어느 쪽이 맞는지 알 수 없다. 틀린 것 같으면 §8에 「기준일 확인」으로 올린다.
      - 광고 도입·폐쇄 결정을 스스로 집행하는 것 (§8로 올리고 사람이 정한다)
      - 검증에 실패한 변경을 미는 것

      범위 밖인데 해야 할 변경은 고치지 말고 **§8에 「승인 필요」로, 제안하는 diff와 함께** 올린다.

      ### 상한

      회차당 `content/` **20파일**. 넘으면 다음 회차로 쪼갠다. 한 커밋에 코퍼스를 통째로
      다시 쓰면 무엇이 무엇을 깨뜨렸는지 갈라낼 수 없다.

      ### 검증 (예외 없음)

```bash
.venv/bin/python .claude/audit/lib/numerics.py
.venv/bin/python .claude/audit/lib/headings.py
.venv/bin/python .claude/audit/lib/contracts.py            # all_checks — 4필드·사전 정합·중복 키·자가검토 예산·리포트 형식
for f in .claude/audit/lib/test_*.py scripts/test_*.py; do .venv/bin/python "$f" || echo "FAIL $f"; done
bash scripts/bootstrap_sandbox.sh && export PATH="$HOME/.local/bin:$PATH"
git submodule update --init --depth 1 themes/PaperMod
hugo --gc --minify && rm -rf public resources
```

      `numerics`·`headings`의 `total`이 0, `contracts`가 `[]`, 단위 테스트 전부 통과,
      Hugo 종료 코드 0이어야 한다. 하나라도 실패하면 **그 파일의 수정을
      `git checkout --`으로 되돌리고** 소견으로만 남긴다.

      본문 산문을 고친 글이 있으면 `post-reviewer` 서브에이전트로 한 건 표집 검토한다.
      검토자가 차단을 내면 그 수정을 되돌린다 — 고치려다 나빠진 것이다.
    </stage>

      | 분류 | 언제 |
      |---|---|
      | 색인 제출 | ③이 "URL is unknown to Google"로 판정한 URL. 회차당 10건까지. |
      | 네이버 | 서치어드바이저 색인 수 조회·수집 요청 (샌드박스 도달 불가) |
      | 기준일 확인 | 원문을 열어야 풀리는 N1·N2, 그리고 §7에서 "틀린 것 같은데 못 고친" 수치 |
      | 승인 필요 | §7 절대 금지 범위의 변경 제안 (제안 diff 첨부) |
      | 광고 | GSC 28일 클릭 ≥ 300 · 색인 페이지 ≥ 40 · 사이트 연령 ≥ 90일 — **전부** 충족 |
      | 폐쇄 상의 | 사이트 연령 ≥ 180일 · 최근 3회 연속 GSC 28일 클릭 < 10 · 색인 커버리지 < 20% — **전부** 충족 |

      광고·폐쇄는 **임계를 실제로 계산한 뒤에만** 올리고 근거 수치를 함께 적는다.
      못 미치면 조용히 넘어가되 현재 값은 리포트 본문에 남긴다 — 다음 회차가 추세를 본다.
    </stage>

    <stage id="9" name="report_memory_commit">
      **순서가 중요하다: 리포트 -> 기억 -> 원장 -> 커밋.** 기억을 커밋 뒤로 미루면
      푸시가 실패했을 때 "했다고 적혀 있는데 실제로는 안 된 것"이 남는다.

      **(1) 리포트** `report/health-YYYY-MM-DD.md`. 헤딩 순서:
      (1) 요약 (2) 운영 연속성 (3) ② 성과 (4) ③ 색인 (5) SEO/GEO 크롤 (6) ⑤ 방향
      (7) 이번 회차에 한 것 (8) 로컬 세션 대기열.
      `monthly_due`면 맨 앞에 `## 월간 현황`을 넣는다 (발행 누계·색인·GSC 추이(지난 달 대비)·자동 수정 누계·다음 달 방향).

      **(2) 기억** — 이 회차의 진짜 산출물이다. `health-memory.md` 머리말의 형식을 그대로 지킨다:

```bash
cat <<'EOF' | .venv/bin/python scripts/health_memory.py append
## <KST> · 회차 <stats의 next_round>

### 지난 회차에서 넘어온 것
### 지금 사이트의 상태
### 무엇을 알게 됐나
### 이번에 시도한 것
### 하지 않기로 한 것
### 다음 회차의 나에게
EOF
```

      네 가지를 반드시 지킨다:

      - **열린 가설을 전부 언급한다.** 판정했으면 `[닫힘]`/`[폐기]`, 아직이면 `[계속]`과 언제 결론 나는지. 조용히 빠뜨리지 않는다.
      - **하지 않기로 한 것을 적는다.** 이유 없이 비어 있으면 다음 회차의 내가 같은 것을 또 검토한다.
      - **관측과 해석을 나눠 쓴다.** 2주 뒤에 해석이 틀렸음을 알아보려면 관측이 따로 남아 있어야 한다.
      - `stats`의 `compact_due`가 참이면 머리말의 압축 규칙대로 오래된 회차를 접는다.

      **(3) 원장**

```bash
.venv/bin/python scripts/health_state.py --record --date <KST> \
  [--monthly] [--notified] --fixes <N> --human-items <N>
```

      **(4) 커밋.** 본문은 `notify-health.yml`과의 계약이므로 글자 그대로 지킨다:

```
health: YYYY-MM-DD 격주 점검

## 점검 요약
알림: 필요 | 불필요
월간 리포트: 예 | 아니오
자동 수정: N건
실험: N건 (신규 N · 판정 N)
사람 작업: N건
발행 누계: N건 / 색인: N건
GSC 28일: 클릭 N · 노출 N
─ 사람이 해야 할 일 ─
* <대기열 항목 또는 없음>
리포트: report/health-YYYY-MM-DD.md
```

      `알림: 필요`는 notification_policy의 넷 중 하나일 때만. 이 줄이 발신 스위치다.
      `─ 사람이 해야 할 일 ─` 아래 불릿만 알림에 실린다.

```bash
git add -A report/ .claude/audit/ .claude/daily-post/ content/ static/ layouts/ hugo.toml
git commit --cleanup=verbatim -m "health: <KST> 격주 점검" -m "<위 본문>"
git pull --rebase origin main
git push origin main
```
    </stage>

    <stage id="10" name="final_report">
      - 각 축 판정, 이번 회차에 한 것(수리 / 실험), 판정한 가설과 결과, 대기열 항목, 알림 발신 여부, 기억 기록 회차 번호, 푸시 결과.
      - **다음 회차가 무엇부터 볼지**를 한 줄로 — 기억에 적은 것과 같은 내용이어야 한다.
    </stage>
